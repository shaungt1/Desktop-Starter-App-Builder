## What this page is for

This page helps a person or an AI coding agent decide which official Tauri plugins an app needs, and then add each one correctly. Tauri is a framework for desktop and mobile apps in which the interface is a web page shown by the operating system's own web view and the backend is a Rust program. A **plugin** is a packaged extension that adds one area of native functionality, such as dialogs or a database. Most official plugins have two halves: a Rust **crate** (a Rust library package, named `tauri-plugin-<name>` and published on crates.io) that must be **registered** on the app builder in `src-tauri/src/lib.rs`, and an npm package of **guest bindings** (the JavaScript or TypeScript functions the interface calls, named `@tauri-apps/plugin-<name>`).

The interface cannot call a plugin until a **capability** grants it a **permission**. A capability is a JSON file in `src-tauri/capabilities/` that lists permissions for named windows; a permission names commands that are allowed or denied; and a **scope** is extra data on a permission that narrows what an allowed command may touch, such as file paths or URLs. Each plugin also ships a **default permission set**, written `<name>:default`, that the plugin authors consider a sensible starting point. These ideas are explained in full in `04-security-capabilities.md`.

The one-line reference table (add command, platforms, version and default permissions) is in `06-plugins.md`; see 06-plugins.md for that table and for the exact behaviour of `tauri add`. This page does not repeat that table. Instead it explains, for each plugin, when to choose it, when to choose something else, the narrowest permission a typical use needs, what mobile builds require, and whether this builder already uses it.

## Decision table: from an app need to a plugin

The table below maps common needs to the plugin or plugins that meet them, with the builder module that already provides the need where one exists. "Base" means the plugin is registered in every Tauri app the builder generates. Read the plugin's own section before adding it, because several needs have a better alternative than the obvious plugin.

| Need | Plugin(s) | Already provided by the builder |
| --- | --- | --- |

| Store structured records and query them with SQL | `sql` (SQLite feature) | `database` module |
| Keep a login token or password encrypted | Not a plugin in this builder: the `secure-storage` module uses the OS key store through the `keyring` crate. The official alternative is `stronghold`. | `secure-storage` module |
| Open a file picker or a "save as" dialog | `dialog` | `filesystem` module (dialog called from Rust) |
| Show a yes/no or message box | `dialog` | `filesystem` module registers it |
| Read or write files from the interface by path | `fs` with a path scope | Not used; the `filesystem` module reads and writes in Rust instead |

| Launch at login | `autostart` | `background` module |
| React to a keyboard shortcut while the app is not focused | `global-shortcut` | Not used |
| Copy to or paste from the clipboard | `clipboard-manager` | Not used |
| Open the app from a `myapp://` link, or receive a sign-in redirect | `deep-link` (+ `single-instance` on desktop) | Base; used by `auth-oidc` |

The table shows that most desktop-app needs are already met by the base template and the six Tauri modules, so an agent should check the builder modules before adding a plugin by hand.

## What the builder already uses

The list below records exactly how this builder uses official plugins, read from its template and module source. It corrects one assumption: the `filesystem` module uses only the `dialog` plugin and does **not** use the `fs` plugin.

1. **Base template** (`tauri/template/src-tauri/src/lib.rs` and `Cargo.toml`). It registers `single-instance` first (desktop only, crate built with the `deep-link` feature; the callback shows the main window), then `deep-link`, `log` (level `Info`), `store`, `opener`, and finally `window-state` (desktop only). In `setup` it calls `register_all()` for deep links on Windows and Linux. `tauri.conf.json` sets `plugins.deep-link.desktop.schemes` to the plan's scheme. The default capability grants only `core:default` and `store:default`; the interface gets no permission for `opener`, `log`, `deep-link` or `window-state`, because those are used from Rust (for example `commands.rs` opens external links through `OpenerExt`). The only plugin npm package in the template is `@tauri-apps/plugin-store` `^2.5.0`.
2. **`database` module**. Adds `tauri-plugin-sql` version `2` with feature `sqlite`, the npm package `@tauri-apps/plugin-sql` `^2.6.0`, registers `tauri_plugin_sql::Builder::default()` with migrations, and adds `capabilities/database.json` granting `sql:default` and `sql:allow-execute` to the `main` window.
3. **`auto-update` module**. Adds `tauri-plugin-updater` and `tauri-plugin-process` (both version `2`), registers `tauri_plugin_updater::Builder::new().build()` and `tauri_plugin_process::init()`, sets `plugins.updater.pubkey` and `plugins.updater.endpoints` placeholders in `tauri.conf.json`, and exposes its own Rust commands `update_check` and `update_install` instead of granting updater permissions to the interface.
4. **`filesystem` module**. Adds `tauri-plugin-dialog` version `2`, registers `tauri_plugin_dialog::init()`, opens dialogs from Rust, and reads or writes only the files the user picked through its own commands `fs_open_text_file` and `fs_save_text_file`. Its source comment says "The interface gets no general file-system permission."
5. **`background` module**. Adds `tauri-plugin-autostart` version `2` and registers `tauri_plugin_autostart::init(MacosLauncher::LaunchAgent, None)`, exposed through its own commands.
6. **`auth-oidc` module**. Adds no plugin of its own; it uses the base `deep-link` plugin to receive the `<scheme>://auth/callback` redirect and the base `opener` plugin to open the sign-in page in the system browser.
7. **`secure-storage` module**. Uses no plugin; it uses the `keyring` crate version `4`.

## autostart

**What it does.** Registers the app to launch automatically when the user logs in to the system. Docs: https://v2.tauri.app/plugin/autostart/

**When to use it.** Tray utilities, sync clients, chat apps and background agents that the user expects to be running after a restart, with a "Start at login" toggle in settings. **When not to.** Do not enable it silently on first run without a user choice; the docs do not require this, but the plugin's JavaScript API exposes `enable`, `disable` and `isEnabled` precisely so the app can offer a toggle. It has no mobile support.

**Platforms.** Windows full, macOS full, Linux full, Android none, iOS none.

**Install.**

```sh
# Any OS, Bun
bun run tauri add autostart
# Any OS, npm
npm run tauri add autostart
```

Rust registration (desktop only, from the docs): `app.handle().plugin(tauri_plugin_autostart::init(tauri_plugin_autostart::MacosLauncher::LaunchAgent, Some(vec!["--flag1", "--flag2"])));` inside `.setup` under `#[cfg(desktop)]`. The second argument is the list of arguments passed to the app when it auto-starts, or `None`. npm package: `@tauri-apps/plugin-autostart` (2.7.0).

**Permissions.** `autostart:default` grants `allow-enable`, `allow-disable` and `allow-is-enabled`, which is exactly what a settings toggle needs. A read-only status display needs only `autostart:allow-is-enabled`. No scope.

**Mobile notes.** Not available on mobile.

**Builder.** Used by the `background` module, with `MacosLauncher::LaunchAgent` and no extra arguments, called from Rust commands.

## barcode-scanner

**What it does.** Uses the phone camera to scan QR codes, EAN-13 and other barcode formats. Docs: https://v2.tauri.app/plugin/barcode-scanner/

**When to use it.** Mobile apps that pair a device by QR code, scan tickets or product codes, or read a Wi-Fi or login QR code. **When not to.** It does nothing on desktop; a desktop app that must read QR codes needs another approach (for example decoding an image file), which the official docs do not cover. The docs' example `scan({ windowed: true, ... })` makes the web view transparent instead of opening a separate camera view, so the interface must be designed to show what is underneath.

**Platforms.** Windows none, macOS none, Linux none, Android full, iOS full.

**Install.**

```sh
# Any OS, Bun
bun run tauri add barcode-scanner
# Any OS, npm
npm run tauri add barcode-scanner
```

Rust registration (mobile only): `app.handle().plugin(tauri_plugin_barcode_scanner::init());` inside `.setup` under `#[cfg(mobile)]`. npm package: `@tauri-apps/plugin-barcode-scanner` (2.5.3).

**Permissions.** `barcode-scanner:default` grants `allow-cancel`, `allow-check-permissions`, `allow-open-app-settings`, `allow-request-permissions`, `allow-scan` and `allow-vibrate`. The docs' minimal example grants only `barcode-scanner:allow-scan` and `barcode-scanner:allow-cancel` in a mobile capability; add `allow-check-permissions` and `allow-request-permissions` if the interface asks for camera access itself. The docs' capability shape for mobile is:

```json
{
  "$schema": "../gen/schemas/mobile-schema.json",
  "identifier": "mobile-capability",
  "windows": ["main"],
  "platforms": ["iOS", "android"],
  "permissions": ["barcode-scanner:allow-scan", "barcode-scanner:allow-cancel"]
}
```

**Mobile notes.** iOS requires `NSCameraUsageDescription` in `src-tauri/Info.ios.plist`, describing why the app uses the camera:

```xml
<key>NSCameraUsageDescription</key>
<string>Read QR codes</string>
```

On Android the plugin's own manifest already declares `android.permission.CAMERA`, `android.permission.VIBRATE` and the feature `android.hardware.camera.any`, so nothing has to be added by hand.

**Builder.** Not used.

## biometric

**What it does.** Checks whether biometric authentication (fingerprint or face) is available and prompts the user to authenticate. Docs: https://v2.tauri.app/plugin/biometric/

**When to use it.** Unlocking a locked section of a mobile app, confirming a sensitive action such as a payment or revealing a stored secret. **When not to.** It proves that the device owner is present; it is not an account login and does not replace server authentication. On Windows and Linux it is not available.

**Platforms.** Windows none, macOS full, Linux none, Android full, iOS full. The docs page text says "on Android and iOS", while the plugin metadata marks macOS as fully supported; `06-plugins.md` notes that `tauri add` treats the plugin as mobile-only, so macOS desktop use needs the dependency moved by hand (**UNVERIFIED** by running it).

**Install.**

```sh
# Any OS, Bun
bun run tauri add biometric
# Any OS, npm
npm run tauri add biometric
```

Rust registration (mobile, from the docs): `app.handle().plugin(tauri_plugin_biometric::Builder::new().build());` inside `.setup` under `#[cfg(mobile)]`. npm package: `@tauri-apps/plugin-biometric` (2.5.0).

**Permissions.** `biometric:default` grants `allow-authenticate` and `allow-status`, which is the narrowest set for "check availability, then prompt". The default set's description states that encrypting and decrypting data with the `biometric_cipher` command is not included and must be enabled with `biometric:allow-biometric-cipher`. No scope.

**Mobile notes.** iOS requires `NSFaceIDUsageDescription` in `src-tauri/Info.ios.plist`:

```xml
<key>NSFaceIDUsageDescription</key>
<string>Authenticate with biometric</string>
```

The plugin's Android manifest declares only its own activity; the docs list no Android manifest entry for the app.

**Builder.** Not used.

## cli

**What it does.** Parses command-line arguments, flags and subcommands defined in `tauri.conf.json` (using the Rust `clap` argument parser) and makes the matches available to JavaScript and Rust. Docs: https://v2.tauri.app/plugin/cli/

**When to use it.** A desktop app that should accept `myapp --verbose`, `myapp open file.txt` or similar from scripts or file associations. **When not to.** If the only arguments are those forwarded from a second launch (for example a deep link), the `single-instance` callback already receives them. The docs warn that on Windows a production app cannot write text back to the calling console by default.

**Platforms.** Windows full, macOS full, Linux full, Android none, iOS none.

**Install.**

```sh
# Any OS, Bun
bun run tauri add cli
# Any OS, npm
npm run tauri add cli
```

Rust registration (desktop only): `app.handle().plugin(tauri_plugin_cli::init());` inside `.setup` under `#[cfg(desktop)]`. npm package: `@tauri-apps/plugin-cli` (2.5.0).

**Permissions.** `cli:default` grants only `allow-cli-matches`, which is already the narrowest useful permission. No scope. The arguments themselves are configured under `plugins.cli`; a minimal example from the docs is:

```json
{
  "plugins": {
    "cli": {
      "description": "Tauri CLI Plugin Example",
      "args": [{ "short": "v", "name": "verbose", "description": "Verbosity level" }]
    }
  }
}
```

**Mobile notes.** Not available on mobile.

**Builder.** Not used.

## clipboard-manager

**What it does.** Reads and writes the system clipboard (text, and on desktop also HTML and images). Docs: https://v2.tauri.app/plugin/clipboard/

**When to use it.** "Copy" buttons for codes, links or generated text; "Paste from clipboard" actions. **When not to.** The default permission set is deliberately empty because, in the plugin's words, "the clipboard can be inherently dangerous"; grant only the direction the app needs. A copy button needs no read permission. Note that the `tauri add` name (`clipboard-manager`) differs from the docs page name (`clipboard`).

**Platforms.** Windows full, macOS full, Linux full, Android partial, iOS partial. "Partial" on Android and iOS means only plain-text content is supported.

**Install.**

```sh
# Any OS, Bun
bun run tauri add clipboard-manager
# Any OS, npm
npm run tauri add clipboard-manager
```

Rust registration: `.plugin(tauri_plugin_clipboard_manager::init())`. npm package: `@tauri-apps/plugin-clipboard-manager` (2.5.0).

**Permissions.** `clipboard-manager:default` grants nothing. Per-command permissions exist for `clear`, `read_image`, `read_text`, `write_html`, `write_image`, `write_secret` and `write_text`. A copy button needs only `clipboard-manager:allow-write-text`; a paste action needs `clipboard-manager:allow-read-text`. No scope.

**Mobile notes.** The docs list no manifest or Info.plist entries.

**Builder.** Not used.

## deep-link

**What it does.** Makes the app the handler for a URL scheme such as `myapp://` (desktop and mobile) or for verified `https://` links (Android App Links and iOS Universal Links), and delivers the opened URL to the app. Docs: https://v2.tauri.app/plugin/deep-linking/

**When to use it.** Receiving an OAuth or OpenID Connect sign-in redirect, opening a specific document from a web page or email, or "open in app" buttons. **When not to.** The docs warn that a user can fake a deep link by passing the URL as a command-line argument; always validate the URL format before acting on it. On macOS deep links work only for an installed bundle in `/Applications`, so they cannot be tested in development there.

**Platforms.** Windows full, Linux full, macOS partial, Android partial, iOS partial. "Partial" means deep links must be registered in configuration; registering a scheme at run time is not supported on those platforms.

**Install.**

```sh
# Any OS, Bun
bun run tauri add deep-link
# Any OS, npm
npm run tauri add deep-link
```

Rust registration: `.plugin(tauri_plugin_deep_link::init())`. On Windows and Linux a link starts a new process with the URL as an argument, so the docs recommend pairing it with `single-instance` built with the `deep-link` feature and registered first. npm package: `@tauri-apps/plugin-deep-link` (2.6.2).

**Permissions.** `deep-link:default` grants `allow-get-current` (read the URL that opened the app). The docs add `core:event:default` because listening with `onOpenUrl` uses the event system. Permissions also exist for `is_registered`, `register` and `unregister`. No scope. The schemes are set in `tauri.conf.json`; the minimal desktop example is:

```json
{ "plugins": { "deep-link": { "desktop": { "schemes": ["something", "my-tauri-app"] } } } }
```

**Mobile notes.** A custom scheme on mobile needs no server: `{ "plugins": { "deep-link": { "mobile": [{ "scheme": ["ovi"], "appLink": false }] } } }`; on iOS the plugin then generates the `CFBundleURLTypes` entries in Info.plist. Verified `https` links need a hosted `.well-known/assetlinks.json` (Android, containing the package name and SHA-256 certificate fingerprints) or `.well-known/apple-app-site-association` (iOS, served over HTTPS with `Content-Type: application/json`, containing `$DEVELOPMENT_TEAM_ID.$APP_BUNDLE_ID`), plus `"appLink": true`, a `host` and optional `pathPrefix` in the config.

**Builder.** Base. Registered in every app with the plan's scheme in `plugins.deep-link.desktop.schemes`, `register_all()` called at startup on Windows and Linux, and used by the `auth-oidc` module for `<scheme>://auth/callback`. The interface is given no deep-link permission; the URL is handled in Rust.

## dialog

**What it does.** Shows native open-file, save-file and folder dialogs, and message, ask (yes/no) and confirm (OK/cancel) boxes. Docs: https://v2.tauri.app/plugin/dialog/

**When to use it.** "Open…", "Save as…", "Choose folder" and confirmation prompts. **When not to.** A dialog only returns a path; to read or write that path the interface also needs `fs` permissions, or a Rust command must do the I/O. The builder's `filesystem` module takes the second route so that the interface never gets general file access. On Android and iOS the dialog returns `content://` URIs and `file://` URIs respectively, not plain paths; the docs say the `fs` plugin accepts these.

**Platforms.** Windows full, macOS full, Linux full, Android partial, iOS partial. "Partial" means there is no folder picker on mobile.

**Install.**

```sh
# Any OS, Bun
bun run tauri add dialog
# Any OS, npm
npm run tauri add dialog
```

Rust registration: `.plugin(tauri_plugin_dialog::init())`. npm package: `@tauri-apps/plugin-dialog` (2.8.3).

**Permissions.** `dialog:default` grants `allow-message`, `allow-save` and `allow-open`. A file picker alone needs only `dialog:allow-open`; a save dialog only `dialog:allow-save`; message, ask and confirm boxes need `dialog:allow-message`. The permissions `dialog:allow-ask` and `dialog:allow-confirm` still exist but are marked deprecated aliases of `allow-message`, to be removed in Tauri v3. No scope.

**Mobile notes.** The docs list no manifest or Info.plist entries.

**Builder.** Used by the `filesystem` module, called from Rust; no dialog permission is granted to the interface.

## fs (file system)

**What it does.** Gives the interface an API to read, write, create, copy, rename, remove, inspect and watch files and directories, restricted by path scopes. Docs: https://v2.tauri.app/plugin/file-system/

**When to use it.** An interface that must work with files in known places, such as reading a cache in the app data folder, writing an export to the Downloads folder, or watching a folder for changes. **When not to.** The docs say that Rust code should use `std::fs` or `tokio::fs` directly; the Rust side of this plugin only manages scopes. For "open the file the user picked", the builder pattern (dialog plus a Rust command that only touches picked files) exposes less. The plugin rejects paths containing `..`.

**Platforms.** Windows full, macOS full, Linux full, Android partial, iOS partial. Notes from the metadata: on Windows, apps installed with MSI or NSIS in `perMachine` or `both` mode need administrator rights to write to `$RESOURCES`; on Linux and macOS there is no write access to `$RESOURCES`; on Android and iOS ("partial") access is restricted to the application folder by default.

**Install.** The `tauri add` name is `fs`.

```sh
# Any OS, Bun
bun run tauri add fs
# Any OS, npm
npm run tauri add fs
```

Rust registration: `.plugin(tauri_plugin_fs::init())`. The `watch` and `watchImmediate` functions require the Cargo feature `watch` (`tauri-plugin-fs = { version = "2.0.0", features = ["watch"] }` in the docs). npm package: `@tauri-apps/plugin-fs` (2.7.1).

**Permissions.** `fs:default` grants `create-app-specific-dirs`, `read-app-specific-dirs-recursive` and `deny-default`: read access to the app's own config, data, local data, cache and log folders, permission to create them, and denial of the web view's data folder. The docs stress that a permission without a scope allows no path, and calls fail with `forbidden path`. The narrowest form is a single command with a scope, as in the docs:

```json
{
  "permissions": [
    "fs:default",
    { "identifier": "fs:allow-exists", "allow": [{ "path": "$APPDATA/*" }] }
  ]
}
```

Ready-made sets also exist, for example `fs:allow-appdata-read-recursive` and `fs:allow-appdata-write-recursive`. `deny` entries win over `allow`. Path variables include `$APPCONFIG`, `$APPDATA`, `$APPLOCALDATA`, `$APPCACHE`, `$APPLOG`, `$HOME`, `$DOCUMENT`, `$DOWNLOAD`, `$DESKTOP`, `$RESOURCE` and `$TEMP` (full list on the docs page). Dotfiles need an explicit path or `plugins.fs.requireLiteralLeadingDot: false`.

**Mobile notes.** Android: to use the audio, cache, documents, downloads, picture, public or video directories, add to `gen/android/app/src/main/AndroidManifest.xml`:

```xml
<uses-permission android:name="android.permission.READ_EXTERNAL_STORAGE"/>
<uses-permission android:name="android.permission.WRITE_EXTERNAL_STORAGE" />
```

iOS: create `src-tauri/gen/apple/PrivacyInfo.xcprivacy` declaring `NSPrivacyAccessedAPICategoryFileTimestamp` with reason `C617.1` (the full XML is on the docs page).

**Builder.** Not used. (The `filesystem` module uses `dialog` and Rust file I/O instead.)

## geolocation

**What it does.** Gets and watches the device position, including altitude, heading and speed where available. Docs: https://v2.tauri.app/plugin/geolocation/

**When to use it.** Mobile apps that show nearby items, record where a photo or report was taken, or track a route. **When not to.** It has no desktop support. Ask for permission only when the feature is used; the docs' example checks and requests permission first.

**Platforms.** Windows none, macOS none, Linux none, Android full, iOS full.

**Install.**

```sh
# Any OS, Bun
bun run tauri add geolocation
# Any OS, npm
npm run tauri add geolocation
```

Rust registration (mobile only): `app.handle().plugin(tauri_plugin_geolocation::init());` inside `.setup` under `#[cfg(mobile)]`. npm package: `@tauri-apps/plugin-geolocation` (2.5.0).

**Permissions.** The plugin has **no default permission set** (no `permissions/default.toml`), so `geolocation:default` does not exist and each permission must be listed. The docs grant `geolocation:allow-check-permissions`, `geolocation:allow-request-permissions`, `geolocation:allow-get-current-position` and `geolocation:allow-watch-position`; a one-off position read needs the first three. Permissions also exist for `clear_permissions` and `clear_watch`. Whether `tauri add` copes with a plugin that has no default set is **UNVERIFIED**; check the capability it writes.

## http

**What it does.** A `fetch`-compatible HTTP client whose requests are sent by Rust (the `reqwest` crate, which the plugin also re-exports for Rust code). Docs: https://v2.tauri.app/plugin/http-client/

**When to use it.** Calling an API from the interface when the API does not send CORS headers for the app's origin. The plugin's JavaScript source states: "The request is performed by the Rust backend instead of the webview, so it is not subject to CORS, but the URL must be allowed by the plugin scope." Also useful when requests must not be limited by the web view's network rules. **When not to.** If the API already allows the app's origin, the web view's own `fetch` needs no plugin, provided the app's Content Security Policy (CSP) lists the host in `connect-src`; the builder's template CSP allows only `'self'`, `ipc:` and `http://ipc.localhost` there, so it must be widened for that route. When the request carries a secret that the interface should not see, write a Rust command that makes the call instead of passing the secret through the interface. Forbidden request headers are dropped unless the Cargo feature `unsafe-headers` is enabled.

**Platforms.** Windows, macOS, Linux, Android and iOS all full.

**Install.**

```sh
# Any OS, Bun
bun run tauri add http
# Any OS, npm
npm run tauri add http
```

Rust registration: `.plugin(tauri_plugin_http::init())`. npm package: `@tauri-apps/plugin-http` (2.8.3).

**Permissions.** `http:default` grants all fetch operations (`allow-fetch`, `allow-fetch-cancel`, `allow-fetch-send`, `allow-fetch-read-body`, `allow-fetch-cancel-body`) but no URLs. The URL scope is what makes it narrow; list only the hosts the app calls:

```json
{
  "permissions": [
    {
      "identifier": "http:default",
      "allow": [{ "url": "https://*.tauri.app" }],
      "deny": [{ "url": "https://private.tauri.app" }]
    }
  ]
}
```

**Mobile notes.** The docs list no manifest or Info.plist entries.

**Builder.** Not used. The `auth-oidc` module uses `reqwest` directly in Rust.

```sh
npm run tauri signer generate -- -w ~/.tauri/myapp.key
```

The minimum configuration is `bundle.createUpdaterArtifacts: true` plus `plugins.updater.pubkey` (the key content, not a file path) and `plugins.updater.endpoints` (HTTPS URLs that may contain `{{target}}`, `{{arch}}` and `{{current_version}}`). Signing, release files and `installMode` on Windows are covered in `07-distribute.md`.

**Permissions.** `updater:default` grants `allow-check`, `allow-download`, `allow-install` and `allow-download-and-install`. A "check and install" button needs `updater:allow-check` and `updater:allow-download-and-install`. No scope.

**Mobile notes.** Not available on mobile.

**Builder.** Used by the `auto-update` module, from Rust commands, together with `process`.

## upload

**What it does.** Uploads a file from disk as the raw request body (not `multipart/form-data`) and downloads a URL to a file, with progress callbacks. Docs: https://v2.tauri.app/plugin/upload/

**When to use it.** Large file transfers with a progress bar, for example uploading a recording to a pre-signed URL or downloading a model or export to disk. **When not to.** Servers that expect `multipart/form-data` uploads need another client (`http` or a Rust command). Use absolute paths (for example from `appDataDir()`); relative paths resolve differently in development and in a bundle. The parent folder must exist, and a failed download leaves its partial file.

**Platforms.** Windows, macOS, Linux, Android and iOS all full.

**Install.**

```sh
# Any OS, Bun
bun run tauri add upload
# Any OS, npm
npm run tauri add upload
```

Rust registration: `.plugin(tauri_plugin_upload::init())`. npm package: `@tauri-apps/plugin-upload` (2.5.0).

**Permissions.** `upload:default` grants `allow-upload` and `allow-download`; grant only the one used. The plugin defines no URL or path scope (its `build.rs` and source register no scope), so any URL and path the interface passes is accepted once permitted.

**Mobile notes.** None listed.

**Builder.** Not used.

## websocket

**What it does.** Opens a WebSocket connection with a Rust client and exposes it to JavaScript. Docs: https://v2.tauri.app/plugin/websocket/

**When to use it.** When the app wants its WebSocket connection to be made by Rust rather than by the web view, for example a chat or live-data client. The docs give no further guidance on when to prefer it; they say only that it opens a connection "using a Rust client". **When not to.** The web view's built-in `WebSocket` is an alternative that needs no plugin, provided the app's Content Security Policy (CSP, the rule list in `tauri.conf.json` that limits what the page may load or connect to) allows the server in `connect-src`; the builder's template CSP allows only `'self'`, `ipc:` and `http://ipc.localhost` there.

**Platforms.** Windows, macOS, Linux, Android and iOS all full.

**Install.**

```sh
# Any OS, Bun
bun run tauri add websocket
# Any OS, npm
npm run tauri add websocket
```

Rust registration: `.plugin(tauri_plugin_websocket::init())`. npm package: `@tauri-apps/plugin-websocket` (2.5.0).

**Permissions.** `websocket:default` grants `allow-connect` and `allow-send`, which a typical client needs. The plugin defines no URL scope.

**Mobile notes.** None listed.

**Builder.** Not used.

## window-state

**What it does.** Saves window size, position and related state on close and restores it on the next launch, for all windows automatically. Docs: https://v2.tauri.app/plugin/window-state/

**When to use it.** Any desktop app with resizable windows. **When not to.** Fixed-size or kiosk windows. To avoid a visible jump, the docs suggest creating windows with `visible: false`; the plugin shows the window after restoring it.

**Platforms.** Windows full, macOS full, Linux full, Android none, iOS none.

**Install.**

```sh
# Any OS, Bun
bun run tauri add window-state
# Any OS, npm
npm run tauri add window-state
```

Rust registration (desktop only): `app.handle().plugin(tauri_plugin_window_state::Builder::default().build());` inside `.setup` under `#[cfg(desktop)]`. npm package: `@tauri-apps/plugin-window-state` (2.5.0).

**Permissions.** `window-state:default` grants `allow-filename`, `allow-restore-state` and `allow-save-window-state`. The automatic save and restore runs in Rust, so the interface needs these only for manual `saveWindowState` or `restoreStateCurrent` calls. No scope.

**Mobile notes.** Not available on mobile.

**Builder.** Base, desktop only, registered as `tauri_plugin_window_state::Builder::new().build()`; no permission is granted to the interface.

## Community plugins

The Tauri plugin overview page (https://v2.tauri.app/plugin/, source `plugin/index.mdx`) has a "Community Plugins" section listing third-party plugins, and states that people can contribute their own on Awesome Tauri (https://github.com/tauri-apps/awesome-tauri), a curated list that has a "Plugins" section. Community plugins are not maintained by the Tauri team, so their platform support, permissions and quality must be checked individually; `tauri add` is documented only for official plugins, and whether it works for a community plugin is **UNVERIFIED**.

## Checklist for adding any plugin

An agent adding a plugin to an app generated by this builder follows these steps in order. Each step names the file it changes so that the change can be checked.

1. **Check whether the builder already provides it.** Read the table in "What the builder already uses". If a module covers the need, enable the module in the plan instead of adding the plugin by hand.
2. **Run the add command** from the project root:

   ```sh
   # Any OS, Bun
   bun run tauri add <add-name>
   # Any OS, npm
   npm run tauri add <add-name>
   ```

   Use the add name, which differs from the page name for `clipboard-manager`, `deep-link`, `fs`, `http`, `log` and `os`.
3. **Check the Rust registration** in `src-tauri/src/lib.rs`. `tauri add` inserts the plugin right after `tauri::Builder::default()` (see 06-plugins.md); in this builder's `lib.rs` that would likely place it before `single-instance` (inferred, **UNVERIFIED** by running it), which must stay first, so move the line after the base plugins or into the owning module's `register` function. Replace any `todo!()` placeholder (`stronghold`, `localhost`). Keep `#[cfg(desktop)]` or `#[cfg(mobile)]` guards for platform-limited plugins, and register `persisted-scope` after `fs`.
4. **Check `src-tauri/Cargo.toml`.** Desktop-only and mobile-only plugins must sit under the matching `[target.'cfg(...)'.dependencies]` table. Add required Cargo features (`sql` driver, `fs` `watch`, `http` `unsafe-headers`, `positioner` `tray-icon`, `single-instance` `deep-link`).
5. **Grant the narrowest permission** in a capability file in `src-tauri/capabilities/`. Following the builder's convention, create a separate file per feature (as `capabilities/database.json` does) rather than widening `default.json`. Replace `<name>:default` with the narrower permissions from the plugin's section when that is enough, add scopes for `fs`, `http`, `opener` and `shell`, and use `"platforms": ["iOS", "android"]` with the mobile schema for mobile-only plugins. Plugins with no default set (`geolocation`, `haptics`) need explicit permissions. Rust-only plugins need nothing.
6. **Add configuration** to `src-tauri/tauri.conf.json` under `plugins.<name>` when the plugin needs it (`cli`, `deep-link`, `sql` preload, `updater`, `fs` options).
7. **Add mobile entries** if the app targets Android or iOS: Info.plist usage descriptions (`NSCameraUsageDescription`, `NSFaceIDUsageDescription`, `NSLocationWhenInUseUsageDescription`, `NFCReaderUsageDescription`), the NFC entitlement and iOS 14 target, the `fs` privacy manifest and Android storage permissions, and deep-link domain files.
8. **Verify** from the project root:

   ```sh
   # Any OS, Bun
   bun run verify
   ```

   In a generated Tauri app this runs type checking, linting, the frontend tests and the Rust tests. Then run the app and exercise the feature; a "not allowed" error at run time means step 5 is incomplete.
