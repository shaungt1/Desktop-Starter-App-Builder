## What this page covers

GitHub Actions is GitHub's built-in automation service: a **workflow** is a YAML file in `.github/workflows/` that runs **jobs** on hosted machines called **runners** when an event happens, such as a push, a pull request or a manual start (`workflow_dispatch`). A job runs a list of **steps**, and a step either runs shell commands or uses a published **action** (a reusable step referenced as `owner/repo@version`).

`tauri-action` is the official action that runs `tauri build` on a runner, creates or updates a GitHub release, uploads the installers to it, and writes the `latest.json` file the Tauri updater reads. This page documents the action's inputs exactly as its `action.yml` defines them, explains the official example workflow, and then gives two complete workflows for an app generated by this builder, which uses Bun: a **release** workflow and a **CI** workflow that verifies pull requests on Windows, macOS and Linux. It ends with mobile builds in CI and with CrabNebula Cloud's pipeline. The secrets referred to here are explained in `11-signing.md`; the short summary in `07-distribute.md` is superseded by this page for CI details.

## `tauri-action` reference

### How it decides which command to run

`src/runner.ts` shows the order in which the action chooses the Tauri CLI. If the `tauriScript` input is set it is used as-is. Otherwise, when the project depends on `@tauri-apps/cli`, the action checks for Vite+ (`vp`), then Yarn, pnpm, Bun and npm. For Bun, `src/utils.ts` looks for a `bun.lockb` or `bun.lock` file (searching up the directory tree) and checks that a `bun` executable is installed; if both are true it runs `bun tauri build`. If no valid CLI installation is detected, it installs `@tauri-apps/cli@v2` globally with npm. A Bun project therefore needs `oven-sh/setup-bun` before the action and a committed `bun.lock`. On macOS runners the action sets `TAURI_BUNDLER_DMG_IGNORE_CI=true` unless you set it yourself (`src/build.ts`). `GITHUB_TOKEN` is required only when the action creates a release or uploads assets (`src/create-release.ts`, `src/upload-release-assets.ts`).

### Inputs

The table below lists every input in `action.yml` at the commit above, with its default and the meaning given in `action.yml` and the README. All inputs are strings in YAML, so `true`/`false` values are written without quotes or in quotes interchangeably.

| Input | Default | Meaning |
| --- | --- | --- |
| `releaseId` | unset | ID of an existing release to upload to. When set, `tagName` and `releaseName` are not used to find a release. |
| `tagName` | unset | Tag of the release to create or upload to. `__VERSION__` is replaced with the app version. If it points to an existing release, `releaseDraft` must match that release's draft status. |
| `releaseName` | `""` | Name of the release to create; required if `releaseId` is not set and no release exists for `tagName`. `__VERSION__` is replaced. |
| `releaseBody` | `""` | Body text of the release. |
| `releaseDraft` | `false` | Whether the release is a draft. Since 1.0.0 the action fails if `true` is set but the existing release is not a draft. |
| `prerelease` | `false` | Whether the release is a prerelease. |
| `releaseCommitish` | SHA of the current commit | Branch or commit the tag is created from; unused if the tag exists. |
| `projectPath` | `.` | Path to the Tauri project root relative to the working directory; must not be gitignored. Relative `--config` paths in `args` resolve against it. |
| `uploadUpdaterJson` | `true` | Upload a `latest.json` for the updater, assuming GitHub Releases is the updater endpoint (only relevant when the updater is configured). Renamed from `includeUpdaterJson` in 1.0.0. |
| `updaterJsonPreferNsis` | `false` | Use the NSIS `-setup.exe` instead of the `.msi` in `latest.json` when both exist. |
| `tauriScript` | `npm`/`pnpm`/`yarn`/`bun tauri`, or `tauri` if the action installed the CLI | Command that runs the Tauri CLI, without `build` or arguments; may be an absolute path (without spaces) to a `tauri-cli` binary. |
| `args` | `""` | Extra arguments for `tauri build`, such as `--target aarch64-apple-darwin` or `--debug`. |
| `retryAttempts` | `0` (README) | Number of retries if the build or the release/upload steps fail. |
| `owner` | owner of the current repository | Account owning the repository to upload to; needs `GITHUB_TOKEN` and a `releaseCommitish` if it differs from the current repository. |
| `repo` | name of the current repository | Repository to upload to; same conditions as `owner`. |
| `githubBaseUrl` | `$GITHUB_API_URL` or `https://api.github.com` | API base URL for GitHub Enterprise; also used in `latest.json`. |
| `releaseAssetNamePattern` | Tauri's own file names | Naming pattern for uploaded assets, with the variables `[name]`, `[mainBinaryName]`, `[version]`, `[platform]`, `[arch]`, `[ext]`, `[mode]`, `[setup]`, `[_setup]`, `[bundle]`. Renamed from `assetNamePattern` in 1.0.0. |
| `uploadPlainBinary` | `false` | Also upload the bare executable; only with `--no-bundle`, and the README warns Tauri has no official portable mode. |
| `uploadWorkflowArtifacts` | `false` | Upload bundles as workflow artifacts (files attached to the workflow run), independent of releases. |
| `workflowArtifactNamePattern` | `[platform]-[arch]-[bundle]` | Naming pattern for workflow artifacts. |
| `uploadUpdaterSignatures` | `true` | Upload the `.sig` files; does not affect `latest.json`. |
| `generateReleaseNotes` | `false` | Use GitHub's release notes API for the title and body; `releaseName` overrides the title and `releaseBody` is prepended. |
| `mobile` | unset | EXPERIMENTAL: `android` or `ios` runs `tauri android build` / `tauri ios build`. iOS works only on macOS runners. System dependencies must be installed by earlier steps, and nothing is uploaded to a store. |

The action's outputs are `releaseId`, `releaseHtmlUrl`, `releaseUploadUrl`, `artifactPaths` and `appVersion`. Note that the older input name `includeUpdaterJson`, still found in older guides, no longer exists; the 1.0.0 changelog renamed it to `uploadUpdaterJson`. Other 1.0.0 changes from the changelog that matter for templates are: Tauri v1 and pre-release v2 versions are no longer supported; `includeRelease`/`includeDebug` were removed (use `args: --debug`); automatic project initialization was removed; and `.app.tar.gz` updater files now include the app version in their names.

If `tagName`, `releaseName` and `releaseId` are all omitted, the action only builds and uploads nothing, which is how the CI workflow below uses it.

## The official example, explained

The Tauri docs' workflow builds on push to a `release` branch (and manually) for macOS on Apple Silicon (`aarch64-apple-darwin`, Macs with M1 and later chips), macOS on Intel (`x86_64-apple-darwin`), Linux x64 (`ubuntu-22.04`), Linux Arm64 (`ubuntu-22.04-arm`, available only to public repositories) and Windows x64. The list below explains the parts a generated app must keep.

1. **Permissions.** `permissions: contents: write` lets the automatically issued `GITHUB_TOKEN` create releases. The docs explain that the token is read-only by default and that a "Resource not accessible by integration" error means write permission is missing; the alternative is Settings, Actions, Workflow permissions, "Read and write permissions".
2. **Matrix.** `strategy.matrix.include` lists one entry per runner and the `args` passed to `tauri build`. Both macOS entries run on `macos-latest`, and `dtolnay/rust-toolchain@stable` installs both Apple targets only on macOS: `targets: ${{ matrix.platform == 'macos-latest' && 'aarch64-apple-darwin,x86_64-apple-darwin' || '' }}`. `fail-fast: false` keeps the other builds running if one fails.
3. **Linux system packages.** On Ubuntu runners the docs install `libwebkit2gtk-4.1-dev libappindicator3-dev librsvg2-dev patchelf xdg-utils`. The `if:` condition must match the platform values in the matrix. Ubuntu 22.04 is used because Linux binaries must be built on the oldest distribution you support (see `13-distribution-stores.md`).
4. **Rust cache.** `swatinem/rust-cache@v2` with `workspaces: './src-tauri -> target'` caches compiled Rust dependencies between runs; the value is written as `<cargo workspace> -> <target directory>` and matches Tauri's default layout.
5. **Frontend dependencies.** The docs run `npm install`; the frontend build itself runs through `beforeBuildCommand` in `tauri.conf.json`.
6. **The action.** `tauri-apps/tauri-action@v1` with `tagName: app-v__VERSION__`, `releaseName: 'App v__VERSION__'`, `releaseDraft: true` and `args: ${{ matrix.args }}`.

The docs also show triggering on tags instead of a branch (`on: push: tags: - 'app-v*'`) and an older approach to Linux Arm builds with `pguyot/arm-runner-action` (emulated, much slower), which GitHub's Arm runners have replaced for public repositories.

## Release workflow for a generated app (Bun)

The workflow below is the official example adapted to Bun and to the builder's conventions. It is triggered by pushing a tag of the form `v1.2.3` or by starting it manually, builds the four desktop targets, and creates a **draft** release so a person reviews it before publishing, in line with `docs/RELEASE_AND_SIGNING.md`. The adaptations from the official example are: `oven-sh/setup-bun@v2` and `bun install --frozen-lockfile` instead of Node.js and npm, a tag trigger instead of the `release` branch, and the Linux Arm runner left as an optional line because it only works in public repositories. The Bun adaptation is not shown in the Tauri docs, and this exact file has not been executed on GitHub's runners; each action reference in it was verified as described above.

Save it as `.github/workflows/release.yml` in the app. `__APP_NAME__` is the builder's placeholder for the display name.

# (Apple Silicon and Intel) and Linux with tauri-action and uploads them to a
# draft GitHub release. Change the trigger, targets or signing blocks here.

  workflow_dispatch:
  push:
    tags:
      - 'v*' # the tag must equal "v" + the version in src-tauri/tauri.conf.json

  publish-tauri:
    permissions:
      contents: write # lets GITHUB_TOKEN create the release
    strategy:
      fail-fast: false
      matrix:
        include:
          - platform: 'macos-latest' # Apple Silicon (M1 and later)
            args: '--target aarch64-apple-darwin'

The list below explains the choices in this file that differ from, or add to, the official example.

1. **Signing blocks are commented out.** A secret that has not been created expands to an empty string, and how the Tauri CLI treats an empty signing variable is **UNVERIFIED** (see `11-signing.md`). Keeping each block commented until its secrets exist avoids failing a first release. The builder should uncomment the updater lines automatically when the auto-update module is selected, because that module sets `bundle.createUpdaterArtifacts` to `true` and the build then needs the private key.
2. **Ad-hoc macOS signing.** Until a Developer ID certificate exists, the app's `tauri.conf.json` should contain `"bundle": { "macOS": { "signingIdentity": "-" } }`, which the GitHub pipeline page recommends for unsigned macOS builds on GitHub releases. Once the macOS block is enabled, `APPLE_SIGNING_IDENTITY` overrides it.
3. **Azure signing on Windows** additionally needs `bundle.windows.signCommand` in the config and, for Artifact Signing, a step that runs `cargo install artifact-signing-cli` (or `relic` installed for Key Vault) before the build; see `11-signing.md`.
4. **Updater endpoint.** With `uploadUpdaterJson` at its default `true`, each release carries a `latest.json`. The updater docs show the matching endpoint `https://github.com/<owner>/<repo>/releases/latest/download/latest.json`. GitHub's "latest" URL ignores drafts and prereleases, so installed apps see a new version only after the draft is published (this follows from GitHub's release behaviour and is **UNVERIFIED** in the Tauri sources).
5. **Releasing.** Increase the version in `src-tauri/tauri.conf.json` (and `package.json`, `src-tauri/Cargo.toml`), commit, then tag and push:

   ```sh
   # any OS, in the app folder
   git tag v1.2.3
   git push origin v1.2.3
   ```

6. **Universal macOS build.** Instead of two macOS entries, the `tauri-action` example `publish-to-auto-release-universal-macos-app-with-signing-certificate.yml` uses one entry with `args: '--target universal-apple-darwin'` (a single binary for both chip types), still installing both Apple targets.

## CI workflow: verify pull requests on three operating systems

The workflow below runs the app's own quality gate (`bun run verify`: type checking, linting, unit tests and Rust tests) on Windows, macOS and Linux for every pull request and push to `main`, and then builds the installers without uploading anything, following the `tauri-action` example `test-build-only.yml` ("If tagName and releaseId are omitted tauri-action will only build the app and won't try to upload any assets"). Because nothing is uploaded, it needs only read permission and no `GITHUB_TOKEN`. One macOS entry (Apple Silicon, the `macos-latest` architecture) is enough to verify. Like the release workflow, this file is an adaptation that has not been executed on GitHub's runners.

Save it as `.github/workflows/ci.yml` (replacing or merging with any existing CI file in the app).

```yaml
# Generated by Desktop Starter App Builder. Verifies every pull request on
# Windows, macOS and Linux: runs the app's quality gate, then builds the
# installers without uploading them.
name: CI

on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

jobs:
  verify:
    strategy:
      fail-fast: false
      matrix:
        platform: [ubuntu-22.04, macos-latest, windows-latest]

    runs-on: ${{ matrix.platform }}
    steps:
      - uses: actions/checkout@v7

      - name: install Linux system packages
        if: matrix.platform == 'ubuntu-22.04'
        run: |
          sudo apt-get update
          sudo apt-get install -y libwebkit2gtk-4.1-dev libappindicator3-dev librsvg2-dev patchelf xdg-utils

      - name: setup Bun
        uses: oven-sh/setup-bun@v2

      - name: install Rust stable
        uses: dtolnay/rust-toolchain@stable

      - name: Rust cache
        uses: swatinem/rust-cache@v2
        with:
          workspaces: './src-tauri -> target'

      - name: install frontend dependencies
        run: bun install --frozen-lockfile

      - name: quality gate
        run: bun run verify

      - name: build installers (no upload)
        uses: tauri-apps/tauri-action@v1
```

The `concurrency` block cancels an older run of the same branch when a new commit arrives, which is the pattern the builder's own CI uses. If a build-only check is too slow for every pull request, the last step can be replaced by `bun run build:e2e` (the template's `tauri build --debug --no-bundle` script), which compiles the app without producing installers.

## Mobile builds in CI

The Tauri docs do not contain a CI guide for Android or iOS. Three sources cover parts of it, as the list below summarizes.

- The Android signing page gives the `keystore.properties` step quoted in `11-signing.md`.
- `tauri-action` has the EXPERIMENTAL `mobile` input. Its README says system dependencies (Xcode, SDKs and so on) must be installed by earlier steps, that the action does not upload to the App Store or Play Store, that Android works on all runners but Ubuntu is recommended because the other required actions typically only work there, and that iOS works only on macOS runners. With the 1.0.0 changelog: "This only includes building (=== running `tauri android|ios build`), installing dependencies and uploading to stores must be done manually."
- CrabNebula's Tauri v2 workflow (fetched) contains complete `build_android` and `build_ios` jobs.

The Android job below is CrabNebula's job with npm replaced by Bun and the CrabNebula upload step removed; its action references are those on CrabNebula's page. It requires the `src-tauri/gen/android` project (created by `tauri android init`) to be committed, because the signing step writes into it, and the `signingConfigs` change from `11-signing.md` to be present in `build.gradle.kts`. It has not been executed, so treat it as **UNVERIFIED**.

```yaml
  build-android:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: oven-sh/setup-bun@v2
      - uses: dtolnay/rust-toolchain@stable
        with:
          targets: aarch64-linux-android,armv7-linux-androideabi,i686-linux-android,x86_64-linux-android
      - name: setup JDK 17
        uses: actions/setup-java@v4
        with:
          java-version: '17'
          distribution: 'temurin'
      - name: setup Android SDK
        uses: android-actions/setup-android@v3
      - name: setup Android NDK
        uses: nttld/setup-ndk@v1
        id: setup-ndk
        with:
          ndk-version: r26d
          link-to-sdk: true
      - name: setup Android signing
        working-directory: src-tauri/gen/android
        run: |
          echo "keyAlias=${{ secrets.ANDROID_KEY_ALIAS }}" > keystore.properties
          echo "password=${{ secrets.ANDROID_KEY_PASSWORD }}" >> keystore.properties
          base64 -d <<< "${{ secrets.ANDROID_KEY_BASE64 }}" > $RUNNER_TEMP/keystore.jks
          echo "storeFile=$RUNNER_TEMP/keystore.jks" >> keystore.properties
      - name: build Android App Bundle
        env:
          NDK_HOME: ${{ steps.setup-ndk.outputs.ndk-path }}
        run: |
          bun install --frozen-lockfile
          bun run tauri android build --aab
      - uses: actions/upload-artifact@v4 # tag exists; inputs UNVERIFIED
        with:
          name: android-aab
          path: src-tauri/gen/android/app/build/outputs/bundle/universalRelease/app-universal-release.aab
```

The changes from CrabNebula's job are listed here so they can be reviewed: Rust targets are installed through `dtolnay/rust-toolchain`'s `targets` input instead of `rustup target add` (same four targets), `--aab` is passed (the Google Play page says the App Bundle is the recommended upload format, at the path used above), and the artifact upload replaces CrabNebula's `release upload`. Alternatively, `tauri-action@v1` with `mobile: android` and `uploadWorkflowArtifacts: true` can replace the last two steps.

For iOS, CrabNebula's `build_ios` job runs on `macos-latest`, adds the `aarch64-apple-ios` target, selects Xcode with `maxim-lobanov/setup-xcode@v1` (`xcode-version: latest-stable`), writes the App Store Connect key to `$RUNNER_TEMP/AuthKey_<key id>.p8`, exports `APPLE_API_KEY_PATH` and `API_PRIVATE_KEYS_DIR`, and builds with `APPLE_API_KEY`, `APPLE_API_ISSUER` and `APPLE_DEVELOPMENT_TEAM` set, running `tauri ios build --export-method app-store-connect`. The key-writing step from that page is:

```yaml
      - name: setup Apple API key
        run: |
          APPLE_API_KEY_PATH="$RUNNER_TEMP/AuthKey_${{ secrets.APPLE_API_KEY_ID }}.p8"
          echo "${{ secrets.APPLE_API_KEY }}" > $APPLE_API_KEY_PATH
          echo "APPLE_API_KEY_PATH=$APPLE_API_KEY_PATH" >> $GITHUB_ENV
          echo "API_PRIVATE_KEYS_DIR=$RUNNER_TEMP" >> $GITHUB_ENV
```

Note the naming in that workflow: the secret `APPLE_API_KEY` holds the **content** of the `.p8` file, while the environment variable `APPLE_API_KEY` given to Tauri holds the **Key ID** (from the secret `APPLE_API_KEY_ID`). Uploading to the stores is covered in `13-distribution-stores.md`; neither `tauri-action` nor Tauri automates it.

## CrabNebula Cloud pipeline

CrabNebula is an official Tauri partner, and CrabNebula Cloud is its distribution platform: a content delivery network (CDN, a network of servers that serve downloads from locations near the user) for installers and updates, integrated with the Tauri updater, with release channels, download buttons and download metrics (see `13-distribution-stores.md` for the service itself). The Tauri pipeline page says to sign in to the Cloud website with a GitHub account, create an organization and application, install the CLI to create a release and upload the Tauri bundles, and that a GitHub Action is provided to run the CLI in workflows.

The action `crabnebula-dev/cloud-release@v0` wraps the CrabNebula CLI (`cn`) and takes two inputs: `command` (the CLI command line) and `api-key`. CrabNebula's Tauri v2 workflow is structured as four stages, listed below.

1. A `draft` job runs `release draft ${{ env.CN_APPLICATION }} --framework tauri`, where the workflow-level `CN_APPLICATION` is `"<org slug>/<app slug>"`.
2. Build jobs (`build_desktop`, `build_android`, `build_ios`) declare `needs: draft`, build the app, and each runs `release upload ${{ env.CN_APPLICATION }} --framework tauri`.
3. A `publish` job, with `needs:` on all build jobs, runs `release publish ${{ env.CN_APPLICATION }} --framework tauri`. CrabNebula's page says this job is optional; releases can be published from the Cloud dashboard instead.
4. Every step passes `api-key: ${{ secrets.CN_API_KEY }}`.

CrabNebula's notes on that page are: the release version comes from `tauri.conf.json` (versions in `Cargo.toml` and `package.json` are ignored); updater signing uses `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` in the build steps' `env`; Linux needs `libwebkit2gtk-4.1-dev`; iOS needs `APPLE_DEVELOPMENT_TEAM`; and `workflow_dispatch` is suggested for testing. Its desktop job uses `actions-rust-lang/setup-rust-toolchain@v1` with `cache: true` instead of `dtolnay/rust-toolchain` plus `rust-cache`, and builds macOS twice on one runner (`--target x86_64-apple-darwin` after `rustup target add x86_64-apple-darwin`, then `--target aarch64-apple-darwin`).

The minimal skeleton below applies that structure to a Bun app for desktop only. The draft, upload and publish commands are exactly as on CrabNebula's page; the Bun install and build lines replace its npm lines. CrabNebula's page states it also offers a Bun variant, which was not captured in this session, so this skeleton is **UNVERIFIED** as a whole.

```yaml
name: Release to CrabNebula Cloud

on:
  workflow_dispatch:

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

env:
  CN_APPLICATION: 'YOUR_ORG_NAME/YOUR_APP_NAME'

jobs:
  draft:
    runs-on: ubuntu-22.04
    steps:
      - uses: actions/checkout@v7
      - uses: crabnebula-dev/cloud-release@v0
        with:
          command: release draft ${{ env.CN_APPLICATION }} --framework tauri
          api-key: ${{ secrets.CN_API_KEY }}

  build:
    needs: draft
    strategy:
      fail-fast: false
      matrix:
        os: [ubuntu-22.04, macos-latest, windows-latest]
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@v7
      - uses: oven-sh/setup-bun@v2
      - uses: dtolnay/rust-toolchain@stable
        with:
          targets: ${{ matrix.os == 'macos-latest' && 'aarch64-apple-darwin,x86_64-apple-darwin' || '' }}
      - uses: swatinem/rust-cache@v2
        with:
          workspaces: './src-tauri -> target'
      - name: install Linux dependencies
        if: matrix.os == 'ubuntu-22.04'
        run: |
          sudo apt-get update
          sudo apt-get install -y libwebkit2gtk-4.1-dev libappindicator3-dev librsvg2-dev patchelf xdg-utils
      - run: bun install --frozen-lockfile
      - name: build (Windows, Linux)
        if: matrix.os != 'macos-latest'
        run: bun run tauri build
        env:
          TAURI_SIGNING_PRIVATE_KEY: ${{ secrets.TAURI_SIGNING_PRIVATE_KEY }}
          TAURI_SIGNING_PRIVATE_KEY_PASSWORD: ${{ secrets.TAURI_SIGNING_PRIVATE_KEY_PASSWORD }}
      - name: build (macOS, both architectures)
        if: matrix.os == 'macos-latest'
        run: |
          bun run tauri build --target x86_64-apple-darwin
          bun run tauri build --target aarch64-apple-darwin
        env:
          TAURI_SIGNING_PRIVATE_KEY: ${{ secrets.TAURI_SIGNING_PRIVATE_KEY }}
          TAURI_SIGNING_PRIVATE_KEY_PASSWORD: ${{ secrets.TAURI_SIGNING_PRIVATE_KEY_PASSWORD }}
      - uses: crabnebula-dev/cloud-release@v0
        with:
          command: release upload ${{ env.CN_APPLICATION }} --framework tauri
          api-key: ${{ secrets.CN_API_KEY }}

  publish:
    needs: build
    runs-on: ubuntu-22.04
    steps:
      - uses: actions/checkout@v7
      - uses: crabnebula-dev/cloud-release@v0
        with:
          command: release publish ${{ env.CN_APPLICATION }} --framework tauri
          api-key: ${{ secrets.CN_API_KEY }}
```

This skeleton differs from CrabNebula's in using the Tauri docs' Linux package list (a superset of CrabNebula's single `libwebkit2gtk-4.1-dev`) and the Tauri docs' Rust setup. Because the updater variables are set unconditionally, it assumes the app has the updater configured.

## Troubleshooting

The list below collects the failure causes stated in the sources.

- **"Resource not accessible by integration"**: the token lacks write permission; add `permissions: contents: write` to the job or enable read and write workflow permissions in the repository settings.
- **Action installs a global CLI instead of using the project's**: Bun was not set up before the action, or no `bun.lock`/`bun.lockb` was found; the action then logs that it could not detect a valid `@tauri-apps/cli` installation.
- **Release already exists as a draft**: when `tagName` points to an existing draft release, `releaseDraft` must be `true`.
- **App not at the repository root**: set `projectPath`; otherwise the action may use a global CLI, and relative `--config` paths resolve incorrectly.
- **DMG icon positions ignored in CI**: a known issue noted on the DMG page (`tauri-apps/tauri#1731`); see `13-distribution-stores.md`.
- **Billing**: the Tauri docs ask readers to read GitHub's usage limits and billing documentation; macOS runners and the Arm emulation workflow consume minutes quickly in private repositories.
