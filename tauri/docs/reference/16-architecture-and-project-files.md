## What this page covers

This page explains how Tauri is put together and what every file in a Tauri project is for, and then covers five development topics that the other files in this set mention only briefly: app icons, bundled resource files, bundled external programs (sidecars), managed state, and keeping Tauri's packages up to date. Commands, events and channels are covered in `05-ipc.md`, configuration keys in `03-config.md`, and mobile specifics in `14-mobile.md`; this page refers to those rather than repeating them.

## 1. How Tauri is put together

### 1.1 The two kinds of process

The process model page describes Tauri as a multi-process architecture "similar to Electron or many modern web browsers". The two kinds of process are described below.

- **The Core process** is the application's entry point and "the only component with full access to the operating system". It is the compiled Rust program. It creates and manages windows, tray menus and notifications, routes all inter-process communication, and should hold global state such as settings and database connections, keeping sensitive data away from the frontend.
- **WebView processes** render the user interface. A **web view** is "a browser-like environment that executes your HTML, CSS, and JavaScript", supplied by the operating system. One Core process manages one or more web views.

The page gives the reason for the split as the principle of least privilege: each part gets only the access it needs, so a compromised or crashed web view cannot take over the system. It follows that secrets and business logic belong in the Core, and that frontend input must be treated as untrusted.

### 1.2 Which web view each operating system uses

Tauri does not ship a browser engine. The process model page says the web view libraries "are not included in your final executable but dynamically linked at runtime", which makes apps much smaller but means rendering differs between systems. The table below combines the process model page and the WebView versions page.

| OS | Web view | Engine | Updated by |
| --- | --- | --- | --- |
| Windows | Microsoft Edge WebView2 | Chromium | WebView2 updates itself; preinstalled on Windows 11, installed by Tauri's installer on older Windows |
| macOS | WKWebView | WebKit | macOS system updates only (unsupported macOS versions get no WebKit updates) |
| Linux | WebKitGTK (`webkit2gtk`, version 4.1 for Tauri 2) | WebKit | The distribution's packages |
| Android | Android System WebView | Chromium | The device's selected WebView provider, usually updatable |
| iOS | WKWebView | WebKit | iOS system updates (the WebView versions page groups iOS with macOS under WebKit) |

### 1.3 The crates and tools

The architecture page lists the parts below. A **crate** is a Rust package.

Core crates (in the `tauri` repository):

- **`tauri`**: "the major crate that holds everything together". It reads `tauri.conf.json` at compile time, injects scripts at runtime, hosts the system APIs, and manages updating.
- **`tauri-runtime`**: the glue layer between Tauri and lower-level web view libraries.
- **`tauri-runtime-wry`**: the runtime implementation for WRY, giving systems-level features such as printing, monitor detection and windowing tasks.
- **`tauri-macros`**: creates the macros for the context, handler and commands (for example `#[tauri::command]`, `generate_handler!`, `generate_context!`), using `tauri-codegen`.
- **`tauri-codegen`**: embeds, hashes and compresses assets and icons, and parses `tauri.conf.json` at compile time.
- **`tauri-utils`**: shared utilities such as config parsing, platform detection, CSP injection and asset handling.
- **`tauri-build`**: applies build-time features for Cargo; it is the `tauri_build::build()` call in every app's `build.rs`.

Upstream crates (separate repositories maintained by the Tauri organization):

- **TAO** creates and manages application windows. It is a fork of the `winit` windowing library, extended with features such as menu bars and the system tray, and supports Windows, macOS, Linux, iOS and Android.
- **WRY** is the cross-platform web view rendering library; Tauri uses it as "the abstract layer responsible to determine which webview is used (and how interactions are made)". The architecture page describes it as supporting the desktop platforms.

Tooling:

- **`@tauri-apps/api`**: the JavaScript/TypeScript library the frontend imports to call the Core and listen to its events.
- **The bundler** (`tauri-bundler`): builds installers for the platform it detects or is told. The architecture page says it supports macOS, Windows and Linux; mobile packages are built through Gradle and Xcode by the `tauri android` / `tauri ios` commands (see `14-mobile.md`).
- **`tauri-cli`** (Rust) and **`@tauri-apps/cli`** (npm wrapper around the Rust CLI, built with napi-rs): the `tauri` command.
- **`create-tauri-app`**: the project scaffolder (see `02-create-project.md`).
- **`tauri-action`**: the GitHub Actions workflow that builds Tauri binaries (see `07-distribute.md`).
- **Plugins**: optional packages that add features; see `06-plugins.md` and `15-mobile-plugin-development.md`.

### 1.4 How the frontend and Core talk

The IPC (inter-process communication) page says Tauri uses **asynchronous message passing**: the processes exchange serialized requests and responses, which is safer than shared memory because the Core can reject or discard any request. There are two primitives, described below.

- **Events** are fire-and-forget, one-way messages that both the frontend and the Core can emit, suited to lifecycle and state changes. Under the hood they use commands, so access to the events API is controlled by permissions.
- **Commands** let the frontend call Rust functions with `invoke`, similar to the browser's `fetch`. A JSON-RPC-like protocol carries them, so all arguments and return values must be serializable to JSON.

Two IPC **patterns** decide how frontend messages reach the Core. The **brownfield** pattern is the default and needs no configuration (`"app": { "security": { "pattern": { "use": "brownfield" } } }`). The **isolation** pattern injects a small, sandboxed "isolation application" in an `<iframe>` that intercepts every IPC message, can validate or modify it, and encrypts it (AES-GCM with a key generated at each start) before it reaches the Core. The docs recommend the isolation pattern whenever it can be used; its configuration is in `04-security-capabilities.md`.

### 1.5 How the build fits together

The project structure page summarizes the build: Tauri "works similar to a static web host". The frontend is first compiled to static files (the `beforeBuildCommand`, writing to `frontendDist`), and then the Rust project is compiled with those files embedded. The frontend setup is therefore "basically the same as if you were to build a static website", which is why server-rendered frameworks must be configured for static output (see `17-nextjs-frontend.md`).

When the built app serves a path, the `tauri` 2.12.5 source (`src/manager/mod.rs`) looks for the file as named, then falls back to `<path>.html`, then `<path>/index.html`, and finally `index.html`. This is why both `about.html` and `about/index.html` layouts work, and why a single-page app's client-side routes resolve to `index.html`.

### 1.6 App size

The App Size page recommends a release profile in `src-tauri/Cargo.toml` for smaller binaries (stable toolchain shown):

```toml
[profile.dev]
incremental = true # Compile your binary in smaller steps.

[profile.release]
codegen-units = 1 # Allows LLVM to perform better optimization.
lto = true # Enables link-time-optimizations.
opt-level = "s" # Prioritizes small binary size. Use `3` if you prefer speed.
panic = "abort" # Higher performance by disabling panic handlers.
strip = true # Ensures debug symbols are removed.
```

It also documents `"build": { "removeUnusedCommands": true }` in `tauri.conf.json`, which removes commands that no capability file allows. It needs `tauri` 2.4, `tauri-build` 2.1, `tauri-plugin` 2.1 and `tauri-cli` 2.4 or newer, works best when capabilities list individual commands rather than `default` sets, and does not account for permissions added at runtime.

## 2. Every project file and what it is for

The tree below shows a typical Tauri 2 project with a JavaScript frontend. It combines the project structure page with the files `create-tauri-app` generates and the files mobile commands add; each entry is explained after the tree.

```text
.
├── package.json              frontend dependencies and scripts ("dev", "build", "tauri")
├── bun.lock / package-lock.json   exact frontend dependency versions
├── index.html                frontend entry page (Vite)
├── vite.config.ts            dev server settings (port 1420, TAURI_DEV_HOST)
├── src/                      frontend source code
└── src-tauri/
    ├── Cargo.toml            Rust crate manifest ([lib] crate-type, tauri, tauri-build, plugins)
    ├── Cargo.lock            exact Rust dependency versions (commit it)
    ├── build.rs              calls tauri_build::build()
    ├── tauri.conf.json       main Tauri configuration (marks the Rust project for the CLI)
    ├── tauri.<platform>.conf.json   optional per-platform overrides
    ├── capabilities/         permission grants for windows (default.json, ...)
    ├── icons/                generated app icons
    ├── src/
    │   ├── main.rs           desktop entry point; calls <lib name>::run()
    │   └── lib.rs            all app code; mobile entry point
    ├── gen/
    │   ├── schemas/          generated JSON schemas for capability autocompletion
    │   ├── android/          Android Studio project (after `tauri android init`)
    │   └── apple/            Xcode project (after `tauri ios init`)
    ├── .taurignore           optional: files `tauri dev` should not watch
    └── target/               Rust build output (never commit)
```

The purpose of each file, from the project structure, configuration files and develop pages, is as follows.

- **`package.json`** holds the frontend's dependencies and scripts. The usual `dev` and `build` scripts are wired to `beforeDevCommand` and `beforeBuildCommand` in `tauri.conf.json`. The configuration page notes that a `"tauri": "tauri"` script is only needed with npm, but `create-tauri-app` adds it for every package manager and this documentation set uses `bun run tauri ...`.
- **Lock files** (`bun.lock`, `package-lock.json`, `Cargo.lock`) pin exact versions so every machine gets the same dependencies. The docs say `src-tauri/Cargo.lock` **should** be committed.
- **`src-tauri/Cargo.toml`** declares the Rust dependencies. The `tauri` and `tauri-build` crates should generally be on the same latest minor version as the Tauri CLI. The `features = []` list of `tauri` is managed automatically by `tauri dev` and `tauri build` from the configuration. The `[lib]` section with `crate-type = ["staticlib", "cdylib", "rlib"]` is needed for mobile.
- **`src-tauri/build.rs`** contains `tauri_build::build()`, used by Tauri's build system.
- **`src-tauri/tauri.conf.json`** is the main configuration, read by the CLI and the runtime. It is also "a marker for the Tauri CLI to find the Rust project". JSON5 (`tauri.conf.json5`) and TOML (`Tauri.toml`) are alternatives when the `config-json5` or `config-toml` feature is enabled on both `tauri` and `tauri-build`. Details are in `03-config.md`.
- **`tauri.linux.conf.json`, `tauri.windows.conf.json`, `tauri.macos.conf.json`, `tauri.android.conf.json`, `tauri.ios.conf.json`** are merged onto the main config on that platform with JSON Merge Patch, where arrays are replaced, not merged.
- **`src-tauri/capabilities/`** is the default folder for capability files, which grant commands and plugin permissions to windows. See `04-security-capabilities.md`.
- **`src-tauri/icons/`** is the default output of `tauri icon` and is referenced by `bundle.icon`.
- **`src-tauri/src/lib.rs`** holds the app code and the function marked `#[cfg_attr(mobile, tauri::mobile_entry_point)]`. Mobile builds compile the app as a library, which is why the code lives here and not in `main.rs`.
- **`src-tauri/src/main.rs`** is the desktop entry point. It calls `app_lib::run()`, where `app_lib` is the `[lib] name` in `Cargo.toml`. The docs advise not modifying it. Its first line, `#![cfg_attr(not(debug_assertions), windows_subsystem = "windows")]`, prevents an extra console window on Windows release builds.
- **`src-tauri/gen/schemas/`** is generated by the build and gives editors autocompletion for capability files. The `create-tauri-app` `.gitignore` excludes `/gen/schemas`.
- **`src-tauri/gen/android/`** and **`src-tauri/gen/apple/`** are the native projects created by `tauri android init` and `tauri ios init`. Mobile icons, manifests, signing settings and entitlements are edited here (see `14-mobile.md`).
- **`.taurignore`** files work like `.gitignore` to stop `tauri dev` rebuilding when matching files change. They are usually placed in `src-tauri` or the Cargo workspace root. `tauri dev --no-watch` disables watching completely.
- **`src-tauri/target/`** is Rust's build output, including installers under `target/release/bundle/`. The docs say it should not be committed.

For a Rust-only app, the project structure page says to remove the frontend files and use `src-tauri/` as the top-level project or as a member of a Cargo workspace.

## 3. App icons

### 3.1 Generating all icons

Tauri ships a default icon set based on its logo, which the icons page says "is NOT what you want when you ship your application". The `tauri icon` command creates every icon each platform needs from one source image, which should be a square PNG or SVG with transparency (default path `./app-icon.png`). Run it from the project root on any OS; Bun first, then npm:

```sh
bun run tauri icon ./app-icon.png
```

```sh
npm run tauri icon ./app-icon.png
```

The options in CLI 2.12.4 are listed below.

- `-o, --output <DIR>`: output folder; default `icons` next to `tauri.conf.json`.
- `-p, --png <SIZES>`: generate only custom PNG sizes instead of the default set.
- `--ios-color <COLOR>`: background colour of iOS icons (default `#fff`).
- `--fit cover|contain`: crop or pad a non-square source; without it a non-square source is rejected.
- A JSON manifest can be passed instead of an image (`default`, `bg_color`, `android_bg`, `android_fg`, `android_fg_scale`, `android_monochrome`) to control Android adaptive and themed icons.

### 3.2 Which icon files each platform needs

The icons page states which files each platform uses; the file list below is what `tauri icon` actually wrote into `src-tauri/icons/` **(tested)**.

| Platform | Files | Notes from the docs |
| --- | --- | --- |
| Windows | `icon.ico` | Must contain layers of 16, 24, 32, 48, 64 and 256 px; for best display in development, the 32 px layer should be first. |
| macOS | `icon.icns` | Layer sizes and names follow Apple's `icns` format. |
| Linux | `32x32.png`, `64x64.png`, `128x128.png`, `128x128@2x.png`, `icon.png` | PNGs must be square, RGBA, 32 bits per pixel. |
| Microsoft Store (AppX) | `Square30x30Logo.png` ... `Square310x310Logo.png`, `StoreLogo.png` | "Currently unused but intended for AppX/MS Store targets." |
| Android | `mipmap-*` launcher icons and adaptive-icon XML | Written into `src-tauri/gen/android/app/src/main/res/` if that project exists, otherwise to `icons/android/` (sizes in `14-mobile.md`). |
| iOS | `AppIcon-*.png` (no transparency) | Written into `src-tauri/gen/apple/Assets.xcassets/AppIcon.appiconset/` if that project exists, otherwise to `icons/ios/`. |

The docs recommend keeping all generated icons even when building for only some platforms, because some files (especially PNGs) are used on more than one platform. The desktop files are listed in `tauri.conf.json`; the default from `create-tauri-app` is:

```json
{
  "bundle": {
    "icon": ["icons/32x32.png", "icons/128x128.png", "icons/128x128@2x.png", "icons/icon.icns", "icons/icon.ico"]
  }
}
```

Mobile icons are not listed in `bundle.icon`; the docs say they go "into the Xcode and Android Studio projects directly", so run `tauri icon` again after `tauri android init` or `tauri ios init`.

## 4. Bundling resource files

**Resources** are extra files shipped with the app that are not part of the frontend build or are too large to embed in the binary, such as language files or data sets. They are declared under `bundle.resources` in `tauri.conf.json`, in one of the two forms shown below.

As a **list**, each file keeps its relative path under the resource directory, called `$RESOURCE`:

```json
{
  "bundle": {
    "resources": ["./path/to/some-file.txt", "../relative/path/to/jsonfile.json", "some-folder/", "resources/**/*.md"]
  }
}
```

The list form follows the rules below.

- `./path/to/some-file.txt` goes to `$RESOURCE/path/to/some-file.txt`.
- An absolute path's root becomes `_root_`, and each `..` becomes `_up_` (so `../relative/path/to/jsonfile.json` goes to `$RESOURCE/_up_/relative/path/to/jsonfile.json`).
- A directory with a trailing slash (`some-folder/`) is copied recursively with its structure.
- `dir/*` copies the files directly in `dir`; `dir/**/*` copies all files recursively; `dir/**` alone is an error.

As a **map**, each source is placed at a chosen target:

```json
{
  "bundle": {
    "resources": {
      "/absolute/path/to/textfile.txt": "resources/textfile.txt",
      "resources/": "",
      "docs/**/*md": "website-docs/"
    }
  }
}
```

In the map form, a glob places all matches flat in the target folder without preserving their sub-folders.

Resolve a resource's real path through Tauri rather than computing it, using the same path syntax as the config. In Rust (`BaseDirectory` is `tauri::path::BaseDirectory`, and `app.path()` needs the `tauri::Manager` trait in scope):

```rust
use tauri::{path::BaseDirectory, Manager};

tauri::Builder::default()
  .setup(|app| {
    let resource_path = app.path().resolve("lang/de.json", BaseDirectory::Resource)?;
    let json = std::fs::read_to_string(&resource_path)?;
    Ok(())
  })
```

In JavaScript:

```ts
import { resolveResource } from '@tauri-apps/api/path';
const resourcePath = await resolveResource('lang/de.json');
```

Reading a resource from JavaScript with the `fs` plugin requires permissions in a capability, for example `"fs:allow-read-text-file"` and `"fs:allow-resource-read-recursive"`. Because of the `_up_` and `_root_` renaming, a scope such as `{ "identifier": "fs:scope", "allow": ["$RESOURCE/**/*"] }` is needed to reach files bundled from outside `src-tauri`.

On **Android**, resources are stored inside the APK as assets. The resolved path is a special `asset://localhost/` URI rather than a file system path, so read it through the `fs` plugin (`app.fs().read_to_string(&resource_path)` in Rust), or copy the files out with the `fs` plugin if a real file is required.

## 5. Bundling external programs (sidecars)

A **sidecar** is a separate executable shipped inside the app, for example a Python program packaged with PyInstaller, so users do not have to install it themselves. Sidecars are listed under `bundle.externalBin`, with paths relative to `src-tauri`:

```json
{
  "bundle": {
    "externalBin": ["binaries/my-sidecar"]
  }
}
```

For each target platform a file with the same name plus `-<target triple>` must exist, for example `src-tauri/binaries/my-sidecar-x86_64-unknown-linux-gnu` on 64-bit Linux or `src-tauri/binaries/my-sidecar-aarch64-apple-darwin` on Apple Silicon macOS (Windows adds `.exe` after the triple). A **target triple** is Rust's name for a platform. Print the host's triple with the first command below (Rust 1.84 or newer), or with the second on older Rust (Linux and macOS):

```sh
rustc --print host-tuple
```

```sh
rustc -Vv | grep host | cut -f2 -d' '
```

Running a sidecar needs the `shell` plugin (`bun run tauri add shell` / `npm run tauri add shell`). The two ways to run it are described below.

- **From Rust:** `app.shell().sidecar("my-sidecar")` (with `use tauri_plugin_shell::ShellExt;`) returns a command; `.spawn()` gives a receiver of `CommandEvent`s (such as `Stdout`) and a child handle that can write to stdin. Rust uses the **file name only** (`"my-sidecar"`), not the path in `externalBin`.
- **From JavaScript:** `Command.sidecar('binaries/my-sidecar')` from `@tauri-apps/plugin-shell`, then `.execute()` or `.spawn()`. JavaScript uses the **same string as in `externalBin`**.

JavaScript calls must be allowed in a capability. Use `shell:allow-execute` for `execute()` and `shell:allow-spawn` for `spawn()`, with the sidecar named and `"sidecar": true`. Arguments are allowed by listing them in order (static strings, or `{ "validator": "<regex>" }` for dynamic ones), or by setting `args` to `true` (any) or `false` (none):

```json
{
  "identifier": "shell:allow-execute",
  "allow": [
    { "name": "binaries/my-sidecar", "sidecar": true, "args": ["arg1", "-a", "--arg2", { "validator": "\\S+" }] }
  ]
}
```

The call must then pass exactly those arguments: `Command.sidecar('binaries/my-sidecar', ['arg1', '-a', '--arg2', 'value'])`.

The sidecar page does not mention mobile. `06-plugins.md` records that the `shell` plugin on Android and iOS supports only opening URLs, so sidecars should be treated as a desktop-only feature (an inference, **UNVERIFIED** by a mobile build).

## 6. Managing state in the Core

Managed state is how the Core keeps data (settings, caches, connections) for the app's lifetime. `05-ipc.md` shows registering and reading state in commands; the state management page adds the rules below.

- Register a value with `app.manage(value)` (or `Builder::manage`) and read it with `app.state::<T>()` or a `State<'_, T>` command parameter. Tauri stores it behind a shared pointer, so **wrapping it in `Arc` is unnecessary**.
- To change shared state, wrap it in a `Mutex` (interior mutability): `app.manage(Mutex::new(AppState::default()))`, then `state.lock().unwrap()`. The lock is released when the guard goes out of scope.
- The standard library `Mutex` is usually right, even in async code. An async mutex such as Tokio's is needed only when the guard must be held across an `.await`, typically for IO resources such as a database connection. An `async` command that takes `State<'_, T>` must return a `Result`.
- Outside commands (other threads, event handlers such as `on_window_event`), get the state through an `AppHandle`: `window.app_handle().state::<Mutex<AppState>>()`. `AppHandle`s are cheap to clone and can be moved into threads.
- **Type mismatches are not caught at compile time.** If a command asks for `State<'_, AppState>` but `Mutex<AppState>` was managed, the `invoke` call is rejected at runtime with a `state not managed for field ...` error, and `Manager::state()` panics. A type alias such as `type AppState = Mutex<AppStateInner>;` avoids the mistake, provided it is not wrapped in a second `Mutex`.

## 7. Calling Rust from the frontend and the frontend from Rust

These topics are covered in `05-ipc.md` (commands, arguments, errors, async commands, channels, events and `eval`). The points below from the source pages are easy to miss and are repeated here.

- Commands without `async` run on the main thread unless declared `#[tauri::command(async)]`.
- A frontend `listen` call returns a Promise of the `unlisten` function. Await it before calling it, and call it when a component unmounts. In React, call it from the `useEffect` cleanup with `unlisten.then((fn) => fn())`. Listeners are removed automatically on page reload, but not on single-page-app route changes.
- Async listeners can process rapidly emitted events out of order; for ordered, high-throughput streams, the docs recommend channels instead of events.

## 8. Updating dependencies

The updating page gives the procedure below.

1. **Update the npm packages.** The docs give the npm form; the Bun form shown first is the equivalent with Bun's `add` command (not in the docs):

   ```sh
   bun add -d @tauri-apps/cli@latest
   bun add @tauri-apps/api@latest
   ```

   ```sh
   npm install @tauri-apps/cli@latest @tauri-apps/api@latest
   ```

   Check for newer versions with `npm outdated @tauri-apps/cli` (Bun: `bun outdated`). A project generated by `create-tauri-app` in this session lists `@tauri-apps/cli` under `devDependencies` and `@tauri-apps/api` under `dependencies`, which is why the Bun form uses `-d` for the CLI.

2. **Update the Rust crates.** Set the versions of `tauri-build` (under `[build-dependencies]`) and `tauri` (under `[dependencies]`) in `src-tauri/Cargo.toml`, then run (any OS):

   ```sh
   cd src-tauri
   cargo update
   ```

   `cargo update` alone already moves to the newest semver-compatible versions (a requirement of `"2"` accepts any 2.x). Prefix a version with `=` to pin it exactly (`tauri-build = { version = "=2.0.0" }`). The docs also mention `cargo outdated` and `cargo upgrade` (from `cargo-edit`) as helpers.

3. **Keep the two sides in step.** The docs require the npm package `@tauri-apps/api` and the crate `tauri` to be on the **same minor version**. For official plugins they require the **exact same version** of the npm package and the crate, for example `@tauri-apps/plugin-fs` 2.2.1 with `tauri-plugin-fs` 2.2.1, because plugin changes may land in patch releases.

The current versions on 2026-10-22 are listed below. The npm versions were checked with `npm view <pkg> version`; the crate versions come from the local Cargo registry, matching `00-index.md`.

| Package | Version |
