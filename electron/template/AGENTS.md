# Agent instructions for __APP_NAME__ (Electron)

These instructions apply to any AI coding agent working in this repository.
Read them fully before making a change.

## What this project is

An Electron desktop application generated by Desktop Starter App Builder. It
is a self-contained project with its own Git history; the builder is not
needed to work on it. `project-plan.json` records the decisions it was built
from, and `.desktop-starter.json` records the builder version and the enabled
modules. This app was generated with the following choices.

| Choice | Value |
| --- | --- |
| Frontend | __FRONTEND__ |
| Interface kit | __UI_KIT__ |
| Package manager | __PACKAGE_MANAGER__ |

`README.md` explains the folder layout. `docs/README.md` indexes the bundled
reference: `docs/SETUP_RESOURCES.md` (tools per operating system),
`docs/electron/` (architecture, makers, signing, publishing and updates, app
stores, Next.js, testing) and `docs/UI_KITS.md` (interface kits, animation and
gestures). Read the relevant page before changing packaging, signing, releases
or the interface kit.

## Before the first change on a new machine

1. Run `bun run doctor`. It checks the tools this app needs and prints the fix for anything missing. It never installs anything.
2. If tools are missing, ask the user before installing. With approval, run `bash scripts/bootstrap.sh --dry-run` (it detects Windows in Git Bash, macOS or Linux; `scripts\bootstrap.ps1` is the PowerShell alternative) to show the plan, then the same command without `--dry-run`.
3. Run `bun install`, then `bun run verify` to confirm a clean baseline before editing anything.

## Commands that prove a change works

Run these from the project root, in this order, and do not report a task as
done until they pass.
1. `bun install` after any change to `package.json`.
2. `bun run verify` — type check (`tsc`), lint and format check (Biome) and unit tests (Vitest).
3. `bun run test:e2e` when the change affects start-up, windows, IPC, navigation, packaging or a module's user flow. On a Linux machine without a display, run `xvfb-run -a bun run test:e2e`.

## Rules

1. **Process boundary.** Node and Electron APIs run only in `src/main` (and `src/main/workers`). The interface in `src/renderer` (and `src/app` with the Next.js frontend) reaches them only through IPC procedures. Never import `electron`, `node:*` or main-process files into interface code, except type-only imports such as `AppRouter`.
2. **Validate every IPC input** with a Zod schema in the procedure definition. Treat the interface as untrusted.
3. **Never weaken the security defaults** in `src/main/window.ts`, `src/main/security.ts`, `src/main/content.ts` and `forge.config.ts` (context isolation, sandbox, no Node integration, fuses, navigation and permission rules, content security policy) unless the user explicitly asks and you explain the risk.
4. **Never expose `ipcRenderer` or Node APIs** through the preload script.
5. **Generated files** — `src/main/modules/registry.ts`, `src/main/ipc/router.ts` and `src/renderer/features/registry.ts` — are rewritten when a module is added with the builder. To add your own feature, either create a module folder and add it to those files following the same pattern, or put the code in your own files and import it from `core-router.ts` and the screens.
6. **Secrets** never go into `app.config.json`, source files or the interface. Store run-time credentials with the secure-storage module (`getSecretStore()`), and build-time secrets in `.env` or CI secrets.
7. **Dependencies.** Use `bun add <pkg>` (or `bun add -d` for tools). Packages that run install scripts must also be listed under `trustedDependencies` in `package.json` when Bun is the package manager. Keep `bunfig.toml`'s hoisted linker; Electron packaging needs a flat `node_modules`.
8. **Database changes** go in `src/main/modules/database/migrations.ts` as a new entry with the next version number. Never edit a migration that has shipped.
9. **Next.js frontend only.** Every route must be exportable to static files: no server actions, route handlers, middleware, `next/image` optimization or dynamic routes without `generateStaticParams`. Mark files that use hooks or the IPC client with `"use client"`, and never call `ipc` at module load (only in effects, query functions or event handlers).
10. **Publishing** (`bun run publish`, pushing a `v*` tag), code signing and store submission need explicit approval from the user for each release.

## Where things are

The table below lists the places most tasks touch.

| Task | Where |
| --- | --- |
| Add a screen (Vite frontend) | A component in `src/renderer/screens/`, registered in `src/renderer/router.tsx`, and a link in `src/renderer/components/app-layout.tsx` |
| Add a screen (Next.js frontend) | A component in `src/renderer/screens/`, a route file `src/app/<route>/page.tsx` that renders it (`"use client"`), and a link in the layout |
| Navigate in code | `NavLink` and `useAppNavigation()` from `src/renderer/lib/navigation.tsx` (works with both frontends) |
| Add a UI component | `bunx shadcn@latest add <name>` (uses `components.json`) or `src/renderer/components/`; Konsta UI components come from `konsta/react` |
| Animation and gestures | `motion/react` and `@use-gesture/react` (see `docs/UI_KITS.md`) |
| Add a native capability | A procedure in `src/main/ipc/core-router.ts` or a module under `src/main/modules/` |
| Long-running background work | A file in `src/main/workers/` started with `utilityProcess.fork(workerPath(name))` |
| Change what the window loads | `src/main/content.ts` (differs per profile and frontend) |
| Change installers, icons or signing | `forge.config.ts`, `assets/`, `docs/electron/02-makers-and-distribution.md`, `docs/electron/03-signing.md` |
| CI and releases | `.github/workflows/ci.yml`, `.github/workflows/release.yml`, `docs/electron/04-publishing-and-updates.md` |
| Change brand colors | `src/renderer/styles/globals.css` |
| App name and description shown in the interface | `src/renderer/lib/app-identity.ts` |
