# __APP_NAME__

__APP_DESCRIPTION__

This desktop application was generated by Desktop Starter App Builder on the
**Electron** base. Electron runs the app as two kinds of process: a **main
process** (Node.js, with full access to the operating system) and one
**renderer process** per window (Chromium, showing the React interface). The
two talk only through a typed, validated bridge described below. The exact
choices used to generate this app are recorded in `project-plan.json`, and the
builder version and enabled modules are recorded in `.desktop-starter.json`.
The main choices are summarized here.

| Choice | Value |
| --- | --- |
| Frontend | __FRONTEND__ |
| Interface kit | __UI_KIT__ |
| Package manager | __PACKAGE_MANAGER__ |

This folder is a self-contained project with its own Git repository. Its
`docs/` folder holds the full reference for building, testing, signing and
shipping it ([`docs/README.md`](docs/README.md) is the index), so it does not
depend on the builder that created it.

## Requirements

Run `bun run doctor` first: it checks every tool below and prints the fix for
anything missing. `bash scripts/bootstrap.sh` (Windows in Git Bash, macOS,
Linux; it detects which) installs what is missing after showing a plan and asking; add `--dry-run` to
only see the plan. [`docs/SETUP_RESOURCES.md`](docs/SETUP_RESOURCES.md) gives
the manual steps for each operating system. The tools are these.
- **Bun** 1.3 or newer, which installs packages and runs scripts.
- **Node.js** 22.17 or newer, because Electron Forge's command-line tool runs on Node.
- **Git**.
- **Linux only, for installers:** `dpkg` and `fakeroot` (`sudo apt install dpkg fakeroot`).

| `bun install`      | Installs packages (the first run downloads Electron).                                                         |
| `bun run dev`      | Starts the app with hot reload for the interface (Vite, or the Next.js dev server) and main-process restarts. |

| `bun run make`     | Builds installers into `out/make/` (Windows Setup.exe, macOS DMG/ZIP, Linux DEB/ZIP).                         |

| `bun run format`   | Rewrites files to the project's formatting rules.                                                             |

## How the code is organized

The table below maps each folder to its responsibility. Files marked
_generated_ are rewritten by the builder whenever a module is added, so edit
the module files they import instead.

| Path                          | Responsibility                                                                                                 |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `src/main/main.ts`            | Start-up: single-instance lock, deep links, security defaults, modules, IPC server, window.                    |
| `src/main/window.ts`          | Creates the main window and remembers its size and position.                                                   |
| `src/main/content.ts`         | What the window shows (this file differs per profile: native, remote or exported).                             |
| `src/main/security.ts`        | Navigation, new-window and permission rules applied to every window.                                           |
| `src/main/deep-links.ts`      | Handling of `__APP_SCHEME__://` links (used by sign-in).                                                       |
| `src/main/ipc/core-router.ts` | Procedures every app has: app info, window controls, theme, opening links.                                     |
| `src/main/ipc/router.ts`      | _Generated._ Combines the core procedures with each module's procedures.                                       |
| `src/main/modules/<id>/`      | Main-process code for one module. `registry.ts` (_generated_) lists the enabled ones.                          |
| `src/main/workers/`           | Each file becomes a separate bundle that runs in its own process (`utilityProcess`).                           |
| `src/preload/preload.ts`      | The only code that sees both the page and Electron. It forwards one message port and exposes nothing else.     |
| `src/renderer/`               | The React interface: `screens/`, `components/` (layout and `ui/`), `features/<id>/` module panels, `lib/`.      |
| `src/app/`                    | Next.js frontend only: one folder per route, each `page.tsx` rendering a screen.                               |
| `docs/`                       | Bundled reference: setup per OS, makers, signing, publishing and updates, app stores, Next.js, testing, UI kits. |
| `scripts/`                    | `doctor.mjs` (machine check), `bootstrap.sh` (install missing tools; Git Bash on Windows) and `bootstrap.ps1` (PowerShell alternative).                      |
| `.github/workflows/`          | `ci.yml` (verify on Windows, macOS, Linux; end-to-end tests on Linux) and `release.yml` (draft GitHub release on a `v*` tag). |
| `.vscode/`                    | Tasks for every command above and recommended extensions.                                                      |
| `app.config.json`             | Non-secret settings from the plan (name, scheme, profile, module options), read by the main process and Forge. |

## The IPC bridge

IPC (inter-process communication) is how the interface asks the main process
to do something. This app runs **oRPC** over a `MessagePort`: the interface
calls `ipc.app.info()` or `ipc.database.createNote({ title })` as ordinary
typed functions, and the TypeScript compiler checks every call against the
main-process router. Every input is validated with **Zod** schemas in the main
process because the interface is treated as untrusted. The preload script does
not expose `ipcRenderer` or any Node API to the page; it only forwards the
message port, and the main process checks the page's origin before accepting
the connection.

To add a procedure, define it in a module's `index.ts` with
`procedure.input(zodSchema).handler(...)` (see `src/main/ipc/procedure.ts`)
and call it from the interface through `ipc.<module>.<procedure>()`.

## Security defaults

The renderer runs with `contextIsolation`, `sandbox` and no Node integration.
Navigation is restricted to trusted origins and other links open in the system
browser. Permission requests from page content (camera, notifications and so
on) are denied unless allow-listed in `src/main/security.ts`. Packaged builds
have Electron's security **fuses** set: the binary cannot be run as plain
Node, ignores `NODE_OPTIONS` and inspector flags, only loads code from its
`app.asar` archive and checks that archive's integrity.

## Configuration and secrets

`app.config.json` holds values that are safe to ship inside the app.
Credentials never go there; tokens at run time go into the secure-storage
module (the operating system's key store). Build-time secrets for signing and
publishing go into `.env`, which is listed in `.gitignore`; `.env.example`
lists every variable.
