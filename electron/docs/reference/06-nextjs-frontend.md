**Next.js** is a React framework. Its **static export** mode turns an app into plain HTML, CSS and JavaScript files at build time, with no Node.js server needed to serve them. This file explains how such an export becomes the interface of an Electron app generated by this builder, why it must be served through a custom URL scheme rather than from `file://`, how to develop against the Next.js development server, and which Next.js features cannot work. The current `next` version on npm is **16.4.2**.

## 1. Two ways the builder supports Next.js

The builder offers two routes, and the right one depends on whether the Next.js code already exists.

1. **The `nextjs` frontend (plan field `"frontend": "nextjs"`, native profile).** The builder generates the Next.js project inside the app: App Router routes in `src/app/` (one `page.tsx` per screen, each rendering a shared screen from `src/renderer/screens/`), `next.config.ts` with `output: "export"`, `distDir: "web-export"` and `images.unoptimized: true`, and a `src/main/content.ts` that serves `web-export/` through the private `app://` scheme in packaged builds and loads the Next.js development server during `bun run dev`. The `build:web` script (`next build`) runs before `package`, `make`, `publish` and `test:e2e`. The Vite renderer is removed (`forge.config.ts` declares no renderer when `app.config.json` says `"frontend": "nextjs"`). Tested: `bun run verify` and the packaged end-to-end tests, including navigation between routes and IPC calls from the static pages, pass on Linux.
2. **The `exported` profile (bring an existing export).** For a Next.js site that lives in its own repository, the exported profile replaces `src/main/content.ts` with a version that serves whatever is in the app's `web-export/` folder, and `forge.config.ts` copies that folder next to `app.asar` as an extra resource so the packaged app works offline. A placeholder `web-export/index.html` is generated; its text tells the user to replace it with the export's output. The bundled React interface in `src/renderer/` stays in the app and is used only for the offline/error screen.

The rest of this page explains the mechanics both routes rely on.

## 2. Configure Next.js for export

Static export is switched on with `output: 'export'` in `next.config.js`. The block below shows the configuration for an Electron interface; each line is explained after it.

```js
/** @type {import('next').NextConfig} */
const nextConfig = {
  output: "export",
  images: { unoptimized: true },
  // trailingSlash: true,
};

module.exports = nextConfig;
```

The list below explains each setting.

1. **`output: "export"`** makes `next build` write the site to the `out/` folder, one HTML file per route (`static-exports.mdx`). Since Next.js 14 this replaces the removed `next export` command.
2. **`images: { unoptimized: true }`** serves every `next/image` source as-is. Image Optimization with the default loader needs a server and is listed as unsupported in a static export; the documented alternatives are this setting (`image.mdx`) or a custom `loader` that points at an external image service.
3. **`trailingSlash`** is optional. By default `/about` is exported as `about.html`; with `trailingSlash: true` it becomes `about/index.html`. The exported profile's request mapping (section 4) accepts both layouts, so leave it unset unless links elsewhere expect trailing slashes.

`distDir` can rename `out/`; the copy command in section 5 then changes accordingly.

## 3. Why `file://` does not work

A Next.js page refers to its scripts and styles with root-absolute URLs such as `/_next/static/chunks/<hash>.js` (`assetPrefix.mdx` shows this form). A root-absolute URL is resolved against the page's origin. Under `file://`, the "root" is the root of the file system, so `/_next/...` points at a folder that does not exist and the page loads without its code. Forge's Vite documentation describes the same failure for Vite builds, which is why Forge sets Vite's `base` to `./` for the template's own interface.

The Electron security checklist adds a second reason (`security.md`, item 18): `file://` pages get more privileges in Electron than in a browser and, after a cross-site scripting bug, could read any file on the machine. Electron recommends serving local pages from a **custom protocol** with `protocol.handle` so the app controls exactly which files can be loaded.

## 4. How the exported profile serves the files

The exported profile's `content.ts` registers a URL scheme named `app` and serves `web-export/` at `app://bundle/`. The steps below follow the code in the order it runs.

1. **Before the app is ready**, `registerContentSchemes()` (called from `main.ts`) runs:

   ```ts
   protocol.registerSchemesAsPrivileged([
     { scheme: "app", privileges: { standard: true, secure: true, supportFetchAPI: true, stream: true } },
   ]);
   ```

   `protocol.md` states that this call is allowed only before `ready` and only once. `standard: true` makes relative and root-absolute URLs resolve as on the web (so `/_next/...` means `app://bundle/_next/...`) and enables `localStorage`, `sessionStorage`, IndexedDB and cookies, which are disabled for non-standard schemes. `secure` treats the scheme like HTTPS, `supportFetchAPI` lets the page `fetch()` from it, and `stream` lets `<video>` and `<audio>` play streamed responses.

2. **When the window loads**, `loadContent()` registers the handler with `protocol.handle("app", ...)` and opens `app://bundle/`. If `web-export/index.html` is missing, it logs an error and shows the bundled offline screen instead.

3. **For each request**, `exportCandidates(root, url)` in `export-path.ts` turns the URL path into candidate files, most specific first, and rejects any path that would leave `web-export/` (for example `app://bundle/../secret`). The mapping mirrors a static web host: a path ending in `/` maps to `index.html` in that folder; a path with a file extension maps to that file; any other path tries `<path>.html` and then `<path>/index.html`. The first existing file is returned with `net.fetch(pathToFileURL(file))`. If none exists, `404.html` from the export is returned with status 404, or plain "Not found".

4. **Trust.** `isTrustedUrl()` in `security.ts` always accepts `app:` URLs, so pages from the export may navigate within `app://bundle/` and may open the typed IPC connection (`src/main/ipc/server.ts` checks the same function).

The unit test `export-path.test.ts` covers the mapping, and the profile's end-to-end test checks that the packaged window's URL starts with `app://bundle/` and shows the expected heading.

Electron 45 also offers `protocol.registerSource(scheme, { routes })`, marked **Experimental**, which serves directories from disk without a JavaScript handler, so requests never wait for the main process. The template does not use it; `protocol.handle` remains the documented, stable method.

## 5. Build and copy the export

The commands below build the Next.js project and copy its output into the Electron app (macOS or Linux shell; run them from the Next.js project folder, with `<electron-app>` replaced by the path of the generated app). They replace the placeholder files.

```bash
bun run build
rm -rf <electron-app>/web-export
cp -R out <electron-app>/web-export
```

```bash
npm run build
rm -rf <electron-app>/web-export
cp -R out <electron-app>/web-export
```

On Windows PowerShell, the copy step is:

```powershell
Remove-Item -Recurse -Force <electron-app>\web-export
Copy-Item -Recurse out <electron-app>\web-export
```

Here `build` is assumed to be the Next.js project's script for `next build`. After copying, `bun run dev` in the Electron app shows the export (in development, `resourcesFolder()` is the project folder, so `web-export/` is read from there), and `bun run make` ships it.

## 6. Development with the Next.js development server

`next dev` serves the app with hot reloading on port 3000 by default (`-p` or `PORT` changes it). With the `nextjs` frontend, the generated `dev` script starts it next to Electron Forge (`concurrently "next dev --port 3000" "electron-forge start"`), and `src/main/content.ts` loads `http://localhost:3000` whenever the app is not running from `app.asar`, retrying once a second until the server answers. The development origin is added to `trustedOrigins()` only in that case, so the page may navigate within it and open the IPC connection during development, and an installed app never trusts it. Set `NEXT_DEV_URL` to use another address.

The exported profile has no development branch: it always loads `app://bundle/`, so each change to an external Next.js project requires a new export copied into `web-export/`. To develop such a project against the running app, generate the app with the `nextjs` frontend instead, or copy the development branch from the `nextjs` frontend's `content.ts`.

## 7. What does not work in a static export

The Next.js documentation lists the App Router features below as unsupported, because they need a server or logic that cannot run at build time. Using one makes `next dev` report an error.

- Dynamic routes with `dynamicParams: true`, or without `generateStaticParams()`
- Route Handlers that read the incoming `Request` (a `GET` handler marked `export const dynamic = 'force-static'` is pre-rendered to a file and does work)
- `cookies()`
- Rewrites, redirects and headers from `next.config.js`
- Proxy (formerly called middleware)
- Incremental Static Regeneration
- Image Optimization with the default loader
- Draft Mode
- Server Actions
- Intercepting Routes

For the Pages Router the list also includes internationalized routing, API routes, `getServerSideProps`, and `getStaticPaths` with `fallback: true` or `'blocking'`. Server Components still work: they run once during `next build`, and their output is saved as static HTML and a payload for client-side navigation. In an Electron app, work that needs a server belongs in the main process instead, reached through IPC procedures (`electron/docs/AGENT_REFERENCE.md`).

## 8. `"use client"` and browser-only code

Client Components are pre-rendered to HTML during `next build`, where `window`, `localStorage` and `navigator` do not exist. The Next.js documentation therefore says to touch these APIs only in the browser, for example inside `useEffect`, in a file marked `'use client'`. The `'use client'` directive goes at the very top of the file, before any import, and marks that file's components as client entry points (`use-client.mdx`).

The template's IPC client (`src/renderer/lib/ipc.ts`) is written for this. It connects on first use instead of at import time, and where no `window` exists it returns a stand-in whose procedures reject, so screens that pass `ipc.app.info` to a query can be pre-rendered without error; the real calls happen in the window. Code that runs at module load must still check `typeof window !== "undefined"` (the crash-reporting module does this before starting Sentry). The generated route files are marked `"use client"` because the screens use React hooks.

## 9. Checklist

Before shipping a Next.js interface, confirm the items below in order.

1. `next.config.js` has `output: "export"` and `images.unoptimized: true` (or a custom loader).
2. `next build` succeeds, which proves no unsupported feature is used.
3. The export is in `web-export/`, including `index.html` and `_next/` (the `nextjs` frontend writes it there directly; for the exported profile, copy the contents of `out/`).
4. Every component that touches `window` or the IPC bridge is in a `'use client'` file and does so inside an effect.
5. `bun run verify` and `bun run test:e2e` pass in the Electron app.
